## 1. 结果与使用体验

| 场景 | 改善前 | 现在 |
|---|---|---|
| 同一会话从作者切到观众 | 作者历史可能继续进入模型 | 使用观众自己的上下文分区 |
| 从角色 A 切到角色 B | 无角色历史分区 | 历史和摘要分别保存、分别读取 |
| 观众或角色读取作者记忆文档 | 可能读到正文、标题或错误中的信息 | 相关文档工具在读取前拒绝 |
| 一批返回 3 个工具调用，只剩 1 次额度 | 可能执行 3 次 | 最多执行 1 次，其余收到明确未执行结果 |
| 上下文已经超预算 | 仍可能请求模型，或删掉摘要/历史 | 先尝试省略可恢复目录，再明确拒绝无法容纳的请求 |
| 工具结果过长 | 只保留截断后的开头 | 返回本轮可用的续取引用 |
| 模型持续调用失败工具 | 可能反复尝试 | 相同失败、总调用次数和时间均有停止边界 |
| 摘要失败后的下一轮 | 原文虽在数据库里，却可能不再进入模型 | 保留未覆盖原文；放不下时显示预算错误 |

页面增加了视角分区说明。预算和时限拒绝通过现有错误区域显示原因与处理建议。
本阶段没有引入新 Agent 框架、向量数据库、任务队列或新增第三方依赖。

## 2. 模块一：视角、角色与项目隔离

### 2.1 原理：同一聊天窗口可以有不同的工作笔记

作者、观众和故事中的角色掌握的信息不同。仅把图谱中的秘密隐藏起来还不够：
模型可能从旧回答或摘要重新读到秘密。

现在每条消息都有一个服务器写入的分区标识，区分作者、观众和具体角色。
会话自身决定所属项目，因此完整的边界是“项目 + 会话 + 视角 + 角色”。
切回某个视角时，恢复该视角自己的历史和摘要。

可以把它理解为同一个文件夹里有不同的笔记本：换角色时翻开对应笔记本，
不会把作者的秘密备忘录一并塞给模型。

### 2.2 实施方式与原因

- 新消息保存 `context_key`；模型传入的工具参数不能修改服务器选择的项目或视角。
- 旧消息统一归入作者分区，原文不删除、不改写。旧数据没有可靠的窄视角标签，无法安全猜测。
- 作者摘要继续保存在原会话上，避免搬动旧数据；观众和角色摘要保存到新的分区表。
- 生成摘要和读取历史使用相同分区条件，避免只隔离原文却遗漏摘要。
- 现有记忆文档没有角色级权限，因此正文、标题、目录和相关工具均限制为作者视角。
- 修复了隐藏实体更新失败时回传真实名称的路径，改用请求方已经提供的引用。

### 2.3 重难点

最容易遗漏的是间接入口，例如摘要、文档标题、失败提示和缓存。
本次除普通聊天外，也保留了草案生成路径经过同一上下文编译边界。
图谱的可见性仍由 perspectives 服务判断，没有在 Agent 里复制另一套权限规则。

### 2.4 异常情况下的稳定程度

测试覆盖作者到观众、不同角色、切回原角色、跨项目以及文档和隐藏名称入口，未出现测试秘密串入。
这是对这些具体场景的验证，不是对任意语言模型输出的绝对保密证明。

**边界说明：**页面仍是创作者管理工具，会保留并展示会话的全部消息。
视角选择限制的是发给模型的信息，不是登录权限或多人账户隔离。

## 3. 模块二：信息来源与提示词边界

### 3.1 原理：规则和资料应分开

项目名称、文档标题甚至正文都可能含有“忽略原规则”这样的文字。
它们应被视为创作资料，不能因为被拼进提示词，就获得系统规则的地位。

现在系统消息只包含固定规则。项目资料放到较低信任级别的数据消息中，并使用固定边界和 JSON 引用。
标题也作为数据保存，不再直接控制分隔符结构。

### 3.2 信息来源记录

本次开始使用上下文清单，记录：

- 当前项目、视角和角色。
- 历史消息的原始 ID，以及当前已保存输入的 ID。
- 指导文档段的 ID 和版本。
- 摘要所属分区与覆盖游标。
- 目录被使用还是因预算省略，以及相应原因。
- 估算方法、输入总量、输出预留和容量。

清单记录来源标识与计量信息，不把消息正文写进这条观测日志。
图谱投影没有被伪装成具有精确实体修订号的记录；目前领域未提供的版本保证仍留给后续阶段。

### 3.3 为什么这样做、哪里最难

这些记录可以帮助解释“本轮使用了什么材料”，也为后续摘要来源回查提供基础。
难点是区分“有来源标识”和“来源内容一定正确”：知道某段摘要来自哪条消息，
不等于证明它没有误解原文。

### 3.4 异常稳定性与限制

格式校验会拒绝不合法作用域、跨分区的已纳入片段和被省略的必需片段。
真正的数据过滤仍在服务器读取边界完成。JSON 包裹只是一层辅助措施，
不能保证模型抵御所有自然语言提示注入。完整摘要语义校验仍属于 E 阶段。

## 4. 模块三：每次模型请求的预算检查

### 4.1 原理：不能只数输入框里的字

模型一次看到的不仅是用户输入，还有系统规则、项目材料、历史、工具说明、工具参数与结果。
它还需要空间生成回答。因此本阶段检查的是整个请求，并预留输出容量。

检查覆盖普通补全、流式补全、工具后的下一次补全、摘要和 JSON 修复重试。
超预算时，检查发生在创建 SDK 客户端和发送请求之前。

### 4.2 当前如何估算

本次采用无新增依赖的保守方法：计算请求 JSON 的 UTF-8 字节数，
再加入每条消息的协议余量和额外协议预留，最后加上输出预留。
中文字符和 emoji 都按实际编码后的字节量计入，不再把英文与中文都粗略当作相同字符成本。

**这不是供应商的精确 Token 数。** Token 是模型切分文本后的计量单位，
不同模型、兼容端点和协议包装可能不同。本方法会较早拒绝一些实际仍可能放得下的请求。
它保证代码按统一的应用预算放行，而不冒充已经测得每个供应商的真实上下文上限。

### 4.3 超预算时如何处理

1. 先保留指导文档、摘要和未被摘要覆盖的历史。
2. 必要时省略可以通过工具重新读取的目录，并在模型上下文中明确说明续取方法。
3. 若仍无法容纳，返回预算错误，不继续发送。
4. 每次工具结果追加后重新检查，之前放行不代表下一次请求也能放行。

工具参数的类型、必填和枚举约束保持；发送给模型时省略重复的字段说明文字，减少不必要的容量消耗。

### 4.4 重难点与异常稳定性

最关键的是后续请求：一个最初很短的问题，经过几轮工具调用后可能变得很长。
测试验证了中文、emoji、大工具说明的边界，以及工具追加和 JSON 修复造成的二次超限。
超限的实际请求不会发送；已经发出的前一请求不可能因此撤销。

长指导文档或积压历史可能导致明确暂停。开启新会话可以减少历史，但若指导文档本身过长，
还需要作者整理指导文档，或在确认真实模型容量后调整配置。不能通过暗中删掉约束解决容量问题。

## 5. 模块四：工具配额、超时与循环停止

### 5.1 逐次配额

每个工具在真正执行前消耗一次额度，包括执行失败的工具。
同一批中超过余额的调用不会执行，但会得到配对的“额度已用完”结果，避免模型协议留下悬空调用。
额度耗尽后的下一请求不再提供工具；模型仍返回工具调用时，本轮明确报错。

### 5.2 多层停止条件

| 边界 | 默认值 | 作用 |
|---|---:|---|
| 每轮工具执行次数 | 4 次 | 限制读取和登记尝试总数 |
| 每轮模型请求次数 | 8 次 | 主回答、摘要等共享上限 |
| 相同工具和参数的重复失败 | 2 次 | 后续相同失败尝试停止本轮 |
| 单个工具耗时 | 15 秒 | 防止读取或登记长时间挂住 |
| 单个模型请求耗时 | 60 秒 | 包含流式结果消费，而不只是等待响应头 |
| 整轮耗时 | 180 秒 | 给整轮工具与模型循环设置总截止时间 |

SDK 自动网络重试已关闭。需要修复 JSON 时，最多一次修复请求，且重新经过预算与次数检查。
没有增加自动重试业务写入的路径。

### 5.3 为什么还要检查工具调用 ID

模型的一次调用和工具的一个结果需要通过 ID 对上号。
空 ID、同批重复 ID 或跨轮重复 ID 会让结果配对失去意义，因此在执行前拒绝。
模型未返回正常聚合结果，也不会被当作成功完成。

### 5.4 异常稳定性与限制

测试验证了工具超时、总时限、重复失败、模型次数用完、禁用工具后仍调用，以及缺少最终结果。
这些场景会结束当前轮并显示错误。Provider 流会显式关闭，减少连接占用。

超时不等于撤销已经提交的业务结果。本阶段工具仍主要登记待确认提案；
批准后的业务写入原子性、断网后的持久状态查询和服务器重启恢复分别仍属于 C、D 阶段。

## 6. 模块五：目录分页与结果续取

### 6.1 原理与实现

目录先展示一页可见条目，模型可用 `list_context_directory` 按返回的下一偏移量继续读取。
工具结果超过字符上限时，返回开头、截断标记和一个不透明续取引用。
模型可通过 `continue_tool_result` 获取后面的部分。

续取保存的是本轮读取结果的快照。引用只存在于本轮的工具上下文中，
另一轮、另一个项目或另一个视角即使持有同一字符串也不能读取。
续取同样消耗正常工具额度，不会绕开工具上限。

### 6.2 这样做的原因

单纯截断只能让模型知道“后面没看到”，却无法继续完成读取。
有明确续取入口，既能限制每次放入上下文的大小，又保留读取完整资料的途径。

### 6.3 重难点与稳定性

测试验证了分页只包含可见条目、中文与 emoji 结果多次续取后可完整拼回，以及跨上下文引用被拒绝。
引用在本轮结束后失效，刷新后不能靠它恢复；这不是长期缓存或持久断点。
若工具额度已经用完，需要下一轮重新读取，而不是无限续页。

## 7. 模块六：数据库迁移与数据保留

### 7.1 本阶段新增结构

- 为消息增加分区字段，旧行默认归入作者。
- 新增观众/角色摘要分区表，以会话和分区标识共同确定一条记录。
- 没有删除或覆盖旧消息、旧摘要、文档段及已保存提案。

共同主键可以避免同一个会话同一个分区出现多份摘要状态。
但它本身不等于完整的并发对话调度；同会话多轮并发的恢复仍属于 D 阶段。

## 9. 配置说明与常见异常处理

新增设置集中在 `backend/app/config.py` 与 `.env.example`。原来的实际 `.env` 没有被改写。
未配置的新项会使用默认值，实际已有配置仍优先。

| 设置 | 默认值 | 对使用者的含义 |
|---|---:|---|
| `AGENT_CONTEXT_MAX_TOKENS` | 8000 | 应用上下文总预算，按本报告的保守方法估算 |
| `AGENT_OUTPUT_RESERVE_TOKENS` | 1024 | 留给模型输出的空间，同时传入模型输出上限 |
| `AGENT_PROTOCOL_RESERVE_TOKENS` | 128 | 为兼容协议额外保留的空间 |
| `AGENT_DIRECTORY_PAGE_SIZE` | 12 | 一次目录页的条目数 |
| `AGENT_TOOL_OUTPUT_MAX_CHARS` | 2000 | 单次工具结果正文长度，超出部分可续取 |
| `AGENT_HISTORY_WINDOW_MESSAGES` | 20 | 触发摘要维护的保留窗口，不再是静默删除阈值 |

遇到预算错误时，先缩短本次任务、减少单轮目标，或开启新会话。
如果仍失败，需要检查作者指导文档体积；单纯缩短输入框内容未必足够。
调整总预算前应确认实际模型支持的容量，不建议为了消除提示而随意调大。

遇到时限或重复工具失败时，按错误提示缩小任务后重试。
若涉及已点击批准的提案，应先检查现有数据；本阶段未解决 C 的批准原子性问题。

## 10. 尚未解决的问题与阶段边界

- **C：**业务写入与批准状态的原子提交、真实读取版本贯穿、幂等与并发竞争。
- **D：**持久运行编号、刷新回读 pending、断流后查询最终状态、旧流与新项目隔离、重启恢复。
- **E：**摘要语义准确性、关键约束覆盖证明、原文恢复入口；本阶段仅停止静默丢弃未覆盖历史。
- **F：**长期记忆提取、跨会话语义召回、冲突和遗忘传播。
- **G：**受控单块编辑与 Skill 协作。
- **H：**真实召回质量、缓存命中与成本优化评估。

因此，当前可以说“模型输入边界和执行上限更可靠”，不能说“整个 Agent 已经具备完整崩溃恢复、
无损长期记忆或所有情况下都不会覆盖用户内容”。这些限制已保留在执行计划中。
