# Agent 改善 E 阶段分析报告

## 结论

E 阶段把“数据库里还有原消息”升级成了“系统能够证明摘要覆盖了哪些原消息，发现
缺口时不会悄悄跳过，而且作者和 Agent 都能按来源找回原文”。它仍然不是 F 阶段的
跨会话长期记忆，也不保证自然语言摘要在文学意义上绝对无损。

## 1. 摘要版本与审计记录

过去每个会话分区只有 `summary` 和 `summary_until_id`。这类似只保存一份改写稿和一个
书签：书签错了，系统无法证明中间有没有漏页。

现在每次摘要尝试都会新增一条不可变的 `agent_summary_versions` 记录，其中包含：

- 会话及精确视角分区；
- 递增版本号、生成模型、摘要策略版本；
- 上一游标、下一游标、按顺序累计的来源消息 ID；
- 输入/输出字符数、验证成功或失败、失败原因；
- 结构化关键项及其原消息来源。

只有覆盖校验成功的版本才能成为活动摘要。空输出、超时、输入或输出超限、来源范围
不连续、精确值校验失败都会留下失败记录，但不会替换上一份可用摘要或推进游标。

## 2. 关键状态如何保留

摘要维护会把约束、决定、未决问题、精确引用和工具失败分成结构化类别。每项保存来源
消息 ID；数字和引号内的精确值还必须能在原消息中逐字找到。验证对象是可机器证明的
事实，例如“来源存在、顺序连续、17 没被改成 70”，而不是声称机器能证明整段文学
语义完全相同。

测试语料覆盖了否定约束、人数、专名、疑问、撤销决定和工具超时。连续两次压缩后，
每个关键项仍能定位到未被改写的原消息。

## 3. 有界压缩与失败恢复

新增四个运行配置：摘要批次消息数、摘要输入字符上限、摘要输出字符上限、原文分页
大小。一次维护只压缩一个完整消息批次；不会为了凑上限把一条消息切半后却宣称整条
已经覆盖。

如果活动游标被破坏，但对应不可变版本仍然完整，系统会从版本记录幂等修复游标，不
再次调用模型。如果版本本身也无法通过来源校验，上下文组装会放弃信任该摘要，从
结构化关键来源和最近消息中做有界原文回补，并明确列出仍被省略、但可以恢复的来源。
原消息始终保留，压缩和恢复都不改写它们。

## 4. 原文恢复工具与权限

新增 `read_conversation_sources`。Agent 可以按来源消息 ID、ISO 时间范围和 offset 分页
读取原文。服务端不接受模型自行指定项目或视角，而是使用当前 `ToolContext` 的会话、
项目、perspective 和 character 分区过滤。测试证明 audience 分区用 author 消息 ID
查询时只得到空结果，不会泄露内容。

## 5. 作者可见的上下文说明

每个持久聊天运行新增可回放的 `context` SSE 事件。事件只包含安全元数据：上下文分区、
活动摘要版本、已使用来源 ID、可恢复但省略的来源 ID，以及是否发生覆盖缺口；不复制
消息正文。前端在会话输入区上方显示可展开说明，刷新或断线重放后仍能恢复这份状态。

“已使用”表示材料被放进模型请求，不表示模型一定正确理解了它；界面没有把来源清单
夸大成语义正确性证明。

## 6. 数据库升级与恢复

迁移 `e3a6f7b8c9d0` 是纯新增：为作者摘要和窄视角摘要增加活动版本引用，并新增摘要版本
表。迁移没有删除或改写消息。实际库升级前先复制：

- `backend/data/backups/agent-e-20260914-1818-before.db`
- `backend/data/backups/agent-e-20260914-1818-rehearsal.db`

演练前后，7 个会话、17 条消息、分区、运行和事件表的旧列逐表哈希一致；完整性检查为
`ok`，外键错误为 0。随后实际库升级到 `e3a6f7b8c9d0`，行数不变，新摘要版本表初始为
0 行。

## 7. 验证边界

验证使用脚本化 provider 和临时数据库，不调用真实计费模型。它证明来源、范围、精确值、
失败状态、原文存在和本轮可召回是不同断言；不宣称已经完成真实模型的长期语义质量
评测。F 阶段的跨会话召回、冲突、接受状态和遗忘没有提前实施。
